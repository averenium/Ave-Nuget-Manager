Per-target-framework update targets

Design for #82. A multi-targeted project can pin one package to a different version per framework; today the panel shows one of them and offers a single shared target for both. Everything not under discussion is drawn exactly as it is today. Type scale, button sizes and colours follow global.css.

What the CLI allows — measured against demo/multi-tfm/, not assumed.

dotnet list package --format json already reports the two pins separately, under their own frameworks[] entries sharing one project path. Both spellings of the condition — on the ItemGroup and on the PackageReference — read the same.

dotnet add package --framework <tfm> edits the matching conditional group and leaves the other one alone. Without the flag it rewrites every conditional group to the one version, which is the bug itself: a net8.0 pin ends up reading 10.0.12.

dotnet remove package has no --framework and removes every conditional reference to the id at once. Removal is a project-level action, and no design here can make it per-framework.

--framework is only honoured when the compatibility check runs. Adding --no-restore makes the CLI ignore it and write the version into every conditional group — so a framework-confined write cannot borrow the batched no-restore shape the entangled-cluster path uses.

For an id the project does not have yet, --framework puts the reference in the matching conditional ItemGroup, and creates that group when there is none. Adding to one framework works from any starting shape.

But on an id the project already references unconditionally, --framework quietly updates that unconditional line — both frameworks move. Splitting a shared reference into per-framework ones is therefore not a CLI call but an edit of our own, and the last section says what it writes.

A project splits only when its frameworks actually disagree about the version. Example.MultiTarget.App above — and every single-target project, and every multi-target project with one unconditional reference — keeps the row it has today: same height, same controls, same order.
The trash sits once per project because that is the only granularity dotnet remove has. The version picker and the apply button move down to the framework, which is the granularity dotnet add --framework has. The two levels on screen are the two levels the CLI actually offers.

The alternative: a flat row per framework

Example.MultiTarget.Core net9.0 9.0.0▾
Example.MultiTarget.Core net10.0 10.0.0▾
One row shorter and it needs no new row type. But it puts a trash on each row that would silently take the other framework with it, and it repeats the project name in the column that is already the narrowest thing in the panel. Recorded as the option considered, not the proposal.

The frameworks are the project's own, and the version is whatever that row's picker is holding — so the menu never asks a second question. A framework that already has the id at that version is there but inert, saying why. Single-target projects get no framework list at all: nothing about their row changes.

Narrowing one project to one framework is a right-click on that project's line — the same menu, so there is one thing to learn and no new button in either place.

When the reference is shared

INSTALL 13.0.4 INTO
net9.0 splits the reference
net10.0 splits the reference
Remove from the project
One unconditional reference covers every framework, and dotnet add --framework would edit that shared line and move all of them without saying so. So this one is not the CLI's to do: choosing a framework here rewrites the reference ourselves, into one conditional reference per framework — the chosen one at the new version, the others left at the version they already had. Nothing changes for a framework the user did not pick.

What the split writes

BEFORE
<ItemGroup>
  <PackageReference Include="Newtonsoft.Json"
                    Version="13.0.1" />
</ItemGroup>
AFTER — net9.0 PICKED, 13.0.4
<ItemGroup Condition="'$(TargetFramework)'=='net9.0'">
  <PackageReference Include="Newtonsoft.Json"
                    Version="13.0.4" />
</ItemGroup>
<ItemGroup Condition="'$(TargetFramework)'=='net10.0'">
  <PackageReference Include="Newtonsoft.Json"
                    Version="13.0.1" />
</ItemGroup>

Where it is written

The repository already edits PackageReference elements directly for non-SDK projects — legacyPackageReference.ts, with the comment-masking from #85 that keeps a comment mentioning a tag from swallowing a real one. The split reuses that path rather than a second XML writer.
One conditional group per framework of the project, in the order the project declares them, and the reference is only ever written at a version that framework already resolved or the user just picked. A project with three frameworks gets three groups, not two and a leftover.

Choosing frameworks when installing — visible, not a right-click

A — badges toggle, one version for the row

Example.MultiTarget.App
Example.MultiTarget.Workers
net8.0 net9.0 net10.0 7.0.0▾
Every badge lit is what happens today — one plain write, no conditional groups. Turning one off narrows the install, and the version box appears only then, because that is when a version of the row's own means anything. Simple, and a project needs two passes to end up with different versions in different frameworks.

B — each badge carries its own version

Example.MultiTarget.App
Example.MultiTarget.Workers
net8.0 7.0.0 net9.0 net10.0 10.0.0
The same toggles, and a lit badge shows the version it will take — defaulting to the one at the top of the panel. One Apply can put 7.0.0 into net8.0 and 10.0.0 into net10.0, which is exactly the case that fails today: Serilog.AspNetCore 10.0.0 needs Logging.Abstractions >= 10.0.0, and net8.0 is pinned to 8.0.0.

What both share

The badges only appear for a project that targets more than one framework. A single-target project keeps the row it has now — a checkbox, a name and a path — and so does every project in a solution that never multi-targets.
All badges lit means the write stays plain and unconditional, so installing into an ordinary project does not start growing conditional groups it never had.
The right-click menu goes away. It was doing this job invisibly.

The list stays complete — crossing a major deliberately is a legitimate thing to do. What changes is the default the apply button proposes: the highest version inside the line this framework is pinned to, which is what dotnet list --outdated --highest-minor reports. Plain --outdated offers 10.0.12 for net9.0, and taking that silently is the whole complaint.

The line above the projects

showing 10.0.0 · also 9.0.0 in 1 project
Today. It counts projects, so two frameworks of one project read as a second project that is not there.
showing 10.0.0 · also 9.0.0 in net9.0
Proposed: when the difference is between frameworks of one project, name the framework instead of counting projects. Across projects the existing wording is untouched.

What does not change

The packages list on the left stays one row per id. A framework split is a property of a project, not of the id, and the row already carries the ↑ when anything beneath it has an update.
A project whose frameworks agree renders through the same row it uses now — the split is the exception, not a new default shape for the section.

Groups tab

Microsoft.Extensions.* net9.0 2
Microsoft.Extensions.* net10.0 2
The two groups already fall apart on their own — the key includes the resolved version, and per-framework pins differ by definition. What is missing is the badge saying which framework a group is, and the --framework on the calls it applies. A group whose members are not framework-scoped carries no badge and looks exactly as it does today.

Still entangled, per framework

Microsoft.Extensions.Http 9.0.20 wants Microsoft.Extensions.Logging.Abstractions >= 9.0.20, so bumping one alone inside net9.0 fails restore with NU1605. The family path already moves members together; what it has to learn is to do that per framework — the net9.0 members as one batch, the net10.0 members as another.
