One new token-free rule, one class, one light-theme line. --color-warning itself is untouched, so the nineteen other places that use it keep the appearance they have.

What the colour is being asked to mean

.pkg-row__version--multi uses --color-warning, which is --vscode-editorWarning-foreground — the same token as a deprecated version, a vulnerability reached through a dependency, a downgrade, a timed-out process and an HTTP log row. Nineteen other places in the stylesheet say “warning” with it.
But several versions across projects is a condition, and across the frameworks of one project it is usually a decision. Painting it with the warning colour files it under problems, next to a vulnerability.
Whatever is chosen, it must be a token of its own rather than a redefinition of --color-warning: the other nineteen users of that token keep the appearance they have.

O · Dark keeps the gold it has; only light is darkened

The asymmetry has to be stated, and the webview has a supported way to state it: VS Code puts vscode-light, vscode-dark or vscode-high-contrast on the body of every webview it renders.

Two constraints on any of these

Green is already in the row. The available-update colour sits in the right-hand column while amber sits in the left. Green and amber are the classic pair a red-green colour deficiency merges, so the two are kept apart by position and by the ↑ mark rather than by hue alone — and that is an argument against introducing a third hue here.
High Contrast themes flatten the palette. global.css already requires a shape rather than a colour for the row marks (#44). The count is text, which is a shape, so K1–K5 all keep their meaning when the hue collapses. K0 does not: strip its colour and the enumeration is just three versions again.
