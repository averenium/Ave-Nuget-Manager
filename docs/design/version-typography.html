How the versions look

Positions are unchanged: the installed version stays in the left column of the row’s second line, the available one stays in the right column, and the sections, marks and colours of state stay as they are. Only the type changes. Each variant below is the same five rows, so they can be read against each other; they combine, and the last pane is the combination worth taking.

0 · Today

The version is set in --font-mono, which resolves to --vscode-editor-font-family — the font the reader chose for their code. It is 11px against the name’s 13px, in the same grey as the feed name directly above it, and it wraps mid-string when the column is too narrow.

Three type families in one row — the UI font for the name, the UI font at 10px for the feed, the editor font at 11px for the version — and the version, the second most useful fact in the row, is the least legible thing on it.

The font is not ours to pick. --font-mono follows the editor font setting, so the list looks different on every machine — a ligature font or a wide one changes how the whole column reads, and we never see it while designing.
No hierarchy. Feed name and version are both --color-tab-inactive, stacked, right-aligned. They read as one grey block instead of two facts of different weight.
A pre-release fills the row. 10.1.0-preview.7.25380.108 is mostly build metadata, and it is set as loudly as the part anyone reads.
The height is not fixed. overflow-wrap: anywhere means a long version wraps and the row grows — so the list shifts while the splitter is dragged.

What none of these change

Where the two versions sit — left column and right column of the same second line, exactly as today.
The green of an available update and the amber of several versions across projects: both already mean something, and both keep meaning it.
The marks, the section headers, the selection and hover treatment, the width of the pane.
Wrapping is the one behaviour that goes: a version ellipsizes with the full string in the tooltip, so a row’s height never depends on the pane’s width.

One honest caveat about A: tabular-nums needs the interface font to carry tabular figures. Segoe UI and the system fonts on macOS and most Linux desktops do; if one does not, the digits fall back to proportional widths — still perfectly readable, just not aligned into a column. That is a softer failure than inheriting an unknown editor font.
