Versions the target framework can use

Design for #107. No plan exists for this issue yet, so this file works directly from the issue text, which is unusually specific about where the problem shows: “The version list, the ↑ button and Groups all offer versions the project's target framework cannot use.” All three turn out to be one shared component plus one shared idea of “what to propose”, so most of this file is about that one component. Sample data uses Example.* names throughout.

Already decided in the issue — 0 comments on #107, so the body is the whole brief so far, and this is drawn rather than redesigned: Part 1 detects the mismatch with no network call, from data the restore already produced (files has lib/ or ref/, but the resolved target's compile is empty), and reports it as a normal compile-time diagnostic. Part 2 reads compatibility from each source's own discovered registration resource (one request per package id, all versions at once), must degrade silently on a source that has none — same as the existing vulnerability scan already does — and reuses resolved credentials rather than assuming anonymous access. The issue's own recommendation sequences the two: Part 1 on its own, Part 2 “together with #86 and #89”. This file still draws Part 2's surface below so a mockup exists whenever that lands — whether it lands with #107 alone or later with those two is outside what this file decides.

What is already true in the code — read from src/webview/, not assumed.

“The version list” is one component, VersionSelect in VersionSelector.tsx. The panel's own picker, every per-project row, every per-framework row (#82), and the Groups tab's family-target picker all render it. Whatever this file settles for that component applies to all four call sites at once, including “Groups”, without a separate design for Groups itself.

The extension already knows each project's target framework(s) — state.packages.projectFrameworks — and already has a precedent for a version that is technically offered but works against the reader's evident intent: versionLine dims a version that would leave the current major (version-select__option--off-line), sets it apart with a rule, and explains why in its tooltip, rather than removing it. It is not hidden, because “crossing a major deliberately is still a legitimate thing to do” — the same sentence applies here with one word changed: crossing to an incompatible framework is not a legitimate thing to do by accident, but the signal that says so is a prediction, not disk fact (next point), so it still shouldn't be the one thing in this list with no way back.

Part 1 and Part 2 of the issue carry different confidence, and the design leans on that difference. Part 1 (no network) reads compile: [] back from an assets file that already exists after every restore — a disk fact about a version already chosen. Part 2 (one HTTP request) reads catalogEntry.dependencyGroups[].targetFramework from the registration resource before a version is chosen at all — which the issue itself calls “a proxy for the lib/ folders rather than a definition of them”. A proxy that can be wrong is not grounds for making a version unreachable.

PkgListRow already carries five marks beside a package name — update, blocked, vulnerable, deprecated, unmapped source — and deliberately did not grow a sixth shape for deprecation: it reuses the vulnerability glyph with its own tooltip. Any new mark this file proposes is held to the same rule.

1 · The version list

Scenario used below: Example.Api targets net8.0 and references Example.Extensions.OpenApi 8.0.11. The feed's versions, newest first: 10.0.12 and 10.0.0 ship lib/net10.0 only; 9.1.0 and 9.0.3 ship both net8.0 and net9.0; 8.0.11 (installed) and 8.0.4 ship net8.0. Clicking the disclosure line swaps it for the two versions it was hiding, dimmed the same way the existing off-line treatment already dims a version outside the current major — this is that same treatment, deferred until asked for. The tooltip leads with what it means for this project — not installable — and only then the reason: not an absent asset, a mismatched one, which lib/net10.0 in the same line makes concrete. A version that is both off-line (#82) and off-framework needs only one explanation; off-framework is the one shown; per-project a version is essentially never both at once in practice, since a major bump is usually also where a project drops old frameworks.

This is one component, so this same picture is what the top “Installed” picker, every project row, every per-framework row, and the Groups family-target picker all show — see §3 for Groups specifically.

2 · The ↑ button

“The ↑ button” is two things today: the small mark beside a package's name in the list (pkg-row__mark--update), and the apply button joined to every version picker (version-apply__btn), whose target is always whatever compareSemVer calls highest. Neither looks at a target framework at all right now — and that splits into two separate questions, each with more than one honest answer.

2a — what the mark and the button's default propose. Same scenario as §1: Example.Api on net8.0, installed 8.0.11, highest compatible 9.1.0, feed's raw latest 10.0.12.

The mark now means “a version that would actually work is available”. 10.0.12 is still reachable through §1's dropdown — only the proposal changes, the resolution #82 already reached for per-framework pins. When nothing compatible is newer, the mark and the row's own version both simply stay put — no ↑, even though the feed's raw latest is higher. Leaving the default alone was the alternative — cheaper, one fewer place compatibility is computed — but the common path is exactly “see an ↑, press the joined button, never open the picker”, and that path would still land on 10.0.12 by default, which is the failure #107 opens with. Cost: rides entirely on Part 2's proxy signal. A false negative there quietly withholds a real update from every reader who only ever looks at the mark and never opens the dropdown.

2b — applying an incompatible version anyway, reached through §1's dropdown regardless of 2a.

Chosen: no extra gate — why

The dropdown's own dimming and tooltip (§1) already said why. Picking it and pressing ↑ applies it like any other version — the same as picking a version the feed marks vulnerable or deprecated does today. A confirmation popup reusing CrossLinePopup/RoslynCapPopup was the alternative — precedented, since both already interrupt for a smaller concern — but it would be a third kind of popup in a panel that already has two, for a path the reader only reaches by deliberately opening a section the UI already called “can't install here”. The dimming already did the interrupting.

3 · Groups

A family's target version already has to satisfy every member (intersectVersions), and a member can already be pinned to one framework of a multi-targeted project (#82, the framework badge on a GroupRow). Framework compatibility is a second condition on the same intersection, not a new mechanism.

Example.Extensions.* — members on net8.0 and net10.0 projects
Example.Extensions.Http
8.0.11 →9.1.0

Every member here happens to sit on a net8.0-or-earlier project, so 9.1.0 (the highest version compatible with all of them) is offered as one shared target exactly as today — nothing to design here beyond feeding the same compatible-version list §1 and §2 use into the existing intersection.

Same family, one member now on a net10.0 project
Example.Extensions.*net8.0
8.0.11 →9.1.0
Example.Extensions.*net10.0
8.0.11 →10.0.12

No single version is compatible with both frameworks, so the family falls apart into its per-framework groups — the same split #82 already draws when members simply disagree on a version. Framework incompatibility is treated as one more reason members disagree, not a reason to invent a second kind of group.

4 · The already-installed, already-broken case (Part 1)

Part 1 is different in kind from §1–3: it is about a version already chosen, already restored, and already missing a compile asset — a fact on disk, not a prediction. The issue's own proposal is to surface it as a normal compile-time diagnostic.

Chosen: Problems panel only — why

⚠ Example.Extensions.OpenApi 10.0.12 has no compile assets for net8.0 (ships lib/net10.0 only)
Example.Api.csproj

This is the mechanism the issue itself asks for — “turns a compile error into a row in Problems” — and it costs nothing extra to design: VS Code's own panel, native icon, native navigation to the reference. No change to PkgListRow at all. A sixth row mark was the alternative — it could have reused the existing warning glyph rather than inventing a shape, exactly as deprecation reuses the vulnerability glyph, so it would not have broken the “no sixth shape” precedent by itself — but it would still have been the row's sixth condition, on a list already asked to stay minimal once before, for a fact the reader meets as a build error the moment they compile anyway.

· What this leaves for whoever implements it

Whether the disclosure line should name the versions instead of just counting them — “N versions that can't install here” is what fits today's narrowest panel, but worth revisiting against the real string lengths once this is built.
Where the compatible/incompatible split is computed — once per package (as §1's scenario assumes) or once per project when a solution has projects on different frameworks — is a data-flow question, not a visual one, and does not change anything drawn above.
Nothing here designs Part 2's HTTP call itself (source discovery, degrading when a feed has no RegistrationsBaseUrl) — the issue already covers that ground and it has no visible surface.
No new colour token is introduced anywhere on this page: §1 and §3 reuse version-select__option--off-line exactly, §2 changes a value, not a style, and §4 stays in VS Code's own Problems panel. That is why this file is dark-only — the one open colour question in the codebase's history for this area (#108, light-theme warning gold) does not recur here.
