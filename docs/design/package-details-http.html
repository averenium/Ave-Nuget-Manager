3 · Before install — the framework group the package has nothing for

The one finding worth stating carefully. A dependency group per framework is what the feed declares, and a package may still ship assets for a framework it declares no dependencies for — so this reports what the feed said and stops there, instead of claiming the package is incompatible.

4 · Before install — reading another framework’s dependencies

The section answers for one framework: the one restore would take. That is the right default and the wrong limit — a library author comparing what a package pulls in on net8.0 against netstandard2.0 can see only one of them, and a package whose group for this project is empty may declare plenty elsewhere. So the framework is selectable, with the picked one still the default. Nothing new is fetched: every group came down with the registration entry.

The heading’s own right-hand line is the control, not a strip of tabs above the rows. That line already named the group, so making it the picker costs no height — the panel’s scarcest dimension — and it holds a long list as easily as a short one. Tabs do not: Newtonsoft.Json declares seven groups, which fit no sidebar at any width and would need a second row, a scroller or an overflow menu, each costing more than it saves.

Rules. The list is the frameworks the feed declares groups for — not the project’s, which the package may say nothing about — newest first, the same order as the framework badges. The default is the group selectCompatibleGroup picks, so the panel opens on what an install would actually use, and says so; that qualifier drops once a framework has been picked by hand, where the reader chose it and knows. A framework this project cannot take stays selectable but is dimmed and reads as browsing, because that is what it is; a group the package declares for no framework at all is listed as any framework, since it can be the default and a default nobody can choose again is a trap. Where the project’s own framework is not known at all — before dotnet list answers, or for good if it failed — the section opens on the newest declared group and drops the “what an install takes” qualifier, because that is a claim only a known project framework supports. The choice resets with the package: a choice about one package’s frameworks means nothing about the next one’s.

Only reachable once a version is installed, and the reason these additions matter for installed packages too: both entries come out of the same registration pages, so the difference between the installed version and the picked one is free to compute. The band replaces nothing — it sits under the version row, appears only while the picked version differs from the installed one, and disappears when they match.

6 · Installed — the version under you was withdrawn

The one fact nothing else in the extension can produce. An unlisted version restores and builds exactly as before, so nothing fails — it simply stops being findable, and a machine that has never restored it may not get it at all.

What is deliberately left out

The package icon. A remote image in the webview means widening the content security policy for every feed, for decoration.
Download counts and reserved-prefix marks. Search-only, and a private feed usually answers neither — a number that appears for one source and not another reads as a fact about the package rather than about the feed.
Owners. In the protocol, absent from most feeds, and already covered by authors for the question a reader is actually asking.
The real per-framework asset list before install. Only the package itself knows it, and reading it means downloading the package to look inside — which is the install.
Every block on this page is drawn only when the feed answered. With the experimental catalog off, a source that is a local folder, or a feed without the metadata resource, the panel is state 1 — no placeholders, no empty labels, no “unknown”.
