The dependents that have to move with a bump

Design for #109. The issue is mostly a backend proposal — walking project.assets.json's reverse graph, a registration lookup for the admitting version — and it settles almost everything about the confirmation UI by pointing at precedent already in the codebase. It leaves one question explicitly open (§3); a second — how the confirmation should render once a bump forces more than one dependent — came up while drawing it (§2). Both are settled below, over two rounds of this file.

The worked case, real, from the issue — Example.Shop.Infrastructure (the repo's own demo/ project) references RabbitMQ.Client 6.8.1 and EasyNetQ 7.8.0, which declares only "6.8.1" as its floor. Bumping the client to 7.2.2 restores clean — the range is satisfied — and breaks at runtime, because 7.x replaced the API 7.8.0 was built against. The registration answer is exact: EasyNetQ 8.1.1 is the first version whose own dependency range admits a 7.x client. The panels below rename the two packages to Example.Messaging.Transport / Example.Messaging.Bus per house convention; the version numbers are the issue's own.

Decided in the issue, drawn as given: Central Package Management gets no special case — one popup, one file behind it. Case 3 (a bare-minimum range crossed by a major — the case above) is never proposed automatically; the user asks for it on that row. Cases 1 and 2 (an actual NU1608/NU1605) are conditions NuGet already reports, so those can interrupt the way CrossLinePopup and RoslynCapPopup already do — no new entry point to draw there. Depth is capped at 10 as a safety valve; the cap that matters for the UI is breadth, the count of packages a proposal is allowed to list.

§3 was the issue's own open question — how the proposal reads once the closure is larger than that breadth cap — and it is settled: a count, and the full list scrolls. §2 raised a different one, not asked by the issue: how the list itself should read once a bump forces more than one dependent. Settled the same way, and for the same reason once a mixed depth-and-breadth case was drawn: one nested view (.gtree__children) rather than a flat list or a separate chain diagram, because a flat list has no room for why a package is on it and a dedicated chain diagram has no way to show a fan-out at all.

Precedent this reuses: BatchLicensePopup for a popup listing several packages' version pairs in one place; ProjectSelectionPopup's popup__item--incompatible for dimming an entry that cannot take the change rather than removing it (#107, the same "dim, don't remove" rule this file leans on again in §3); CrossLinePopup/SplitReferencePopup for a plain, non-checkable list stating a consequence and one decisive action — the shape §2 follows, because a cascade's members are not independent the way a licence batch's are: leaving one out defeats the point of taking the rest.

1 · Where this starts

Two different triggers, already decided, drawn once each rather than as a choice.

Cases 1–2 — interrupts the apply, like today's other popups

Picking a version that trips NU1608 or downgrades below another package's floor already fails or warns on restore. The cascade check sits beside the existing needsRoslynUpgradeConfirm / cross-line checks in requestApply — no new row control, no new visual here, just one more condition that can open §2's popup instead of writing straight through.

Case 3 — asked for on the row, via the existing right-click menu

Example.Messaging.Transportnuget.org
6.8.17.2.2
Check what else has to move
Block updates

One line added to BlockedPackageMenu's existing right-click menu rather than a new icon on an already-minimal row. A bare-minimum range crossed by a major is a heuristic (measured at ~2% of declarations even carrying an explicit range), so it stays something the reader reaches for, not something pushed at them.

2 · The confirmation

Not checkable rows: a cascade's members are causally linked, so a plain list and one decision — the shape CrossLinePopup already uses — rather than BatchLicensePopup's per-row opt-out. How that list is rendered was open for two rounds; both are settled below.

Chosen: one nested view, for every shape — why

Example.Messaging.Transport

7.2.2 is outside what Example.Messaging.Bus 7.8.0 was built against. One version of it admits the new client:

Example.Messaging.Transport
6.8.1 → 7.2.2
Example.Messaging.Bus 7.8.0 → 8.1.1
requires ≥7.2.0

Restore stays green either way — this is caught by range, not by the compatibility NuGet itself checks. Taking both is the smallest change that keeps them working together.

Wording still mirrors CrossLinePopup: state the fact, one decisive action, no checkboxes — a cascade's members are not independent, so leaving one out defeats the point. What changed across two rounds of this file is only the list itself: a flat popup__list-plain lost to .gtree__children, the same indentation §3's fan-out already needed, because the flat version had nowhere to put why Bus is here — the registration range, requires ≥7.2.0, straight from catalogEntry.dependencyGroups[].dependencies[].range — without a third line per row. One mechanism, not two: the same nesting reads as this for one dependent, a list for many unrelated ones (§3), a staircase for a real chain, and both at once when the walk returns both. Example.Shop.Infrastructure stays out of the popup itself, implied by the row it was opened from.

Three hops — the same nesting, one step deeper each time

Example.Messaging.Transport

7.2.2 forces two other packages to move in turn.

Example.Messaging.Transport
6.8.1 → 7.2.2
Example.Messaging.Bus 7.8.0 → 8.1.1
requires ≥7.2.0
Example.Messaging.Outbox 3.1.0 → 3.4.0
requires ≥8.1.0

Corrected from the last round, which called this "a single column" — it is not. Indentation shows it is Transport → Bus → Outbox, not three packages independently tied to Transport, but each hop also marches the row another ~33px to the right, and Outbox's row here is already giving up close to a fifth of the popup's width to do it. Cost, honestly open: this file has not drawn a chain past two hops, and #109's own depth cap is 10. Nothing here says the staircase still reads at hop 5 rather than needing a cap of its own, or a different treatment — a flatter one, an id that starts eliding — once a real deep case exists to check it against.

All 23 sit at depth 1, siblings under one root, none depending on each other — there is no chain to show, so the same .gtree__children the panels above use for a hop renders these flush with no indentation to spend. This and the three-hop panel above are the two clean extremes; the reverse-graph walk is under no obligation to hand back either one on its own, which is exactly what the next panel draws.

Proof it generalises — deep in one branch, wide in the rest

The case an arbitrary reverse-graph walk actually produces: not a pure chain, not a pure fan-out, but both at once. Example.Extensions.Http is one of three direct dependents here exactly as in the fan-out panel, but taking it to 9.0.0 in turn forces Example.WebFramework.Client, which has no reason to move otherwise — the same shape as the three-hop panel, one branch over.

Example.Extensions.Abstractions

9.0.0 needs 4 other packages to move with it.

Example.Extensions.Abstractions
8.1.0 → 9.0.0
Example.Extensions.Http 8.1.0 → 9.0.0
Example.WebFramework.Client 3.1.0 → 3.4.0
requires Http ≥9.0.0
Example.Extensions.Logging 8.1.0 → 9.0.0
Example.Extensions.Caching 8.1.0 → 9.0.0

The same .gtree__children indentation every other panel in §2 and §3 uses, nested one level further for the one branch that needs it — not a third diagram type, and no code that has to decide "is this a chain or a fan-out" before it can render. Example.Extensions.Logging and Example.Extensions.Caching stay flush with Http because they do not have children of their own — the indentation is only ever as deep as the graph actually is, which is the whole reason one mechanism covers the plain list, the staircase, and this at once. Cost: real tree-rendering code — recursive, not a fixed two- or three-row template — and the CSS guide line has to keep lining up correctly at every depth and popup width the walk can produce, which the fixed-depth panels above never had to prove.

Dead end — no version admits the target

Example.Messaging.Transport

No version of Example.Messaging.Bus declares a range wide enough for 7.2.2 — every release stops at [6.0.0, 7.0.0). Taking this version breaks Example.Messaging.Bus at runtime with nothing that would bring it back in line.

This bump isn't safe yet. Blocking it keeps it off every batch update until that changes.

The issue calls this a first-class outcome, not an error: “Block updates exists for exactly this.” Same popup shape, one row instead of a list, and the primary action is SET_PACKAGE_BLOCKED — the exact call BlockedPackageMenu already sends — rather than a dead end with only Cancel.

3 · When the closure is larger than the breadth cap

Scenario: bumping a widely-depended-on package (Example.Extensions.Abstractions, mirroring how Microsoft.Extensions.* fans out in the demo solution) surfaces 23 dependents needing a move. This was the one thing #109 itself left open, and it is settled below: it stays a plain, flush list, for the same reason §2 gives — 23 siblings with no edges between them have no depth for the nesting to spend.

Chosen: the count, and the full list scrolls — why

Example.Extensions.Abstractions

9.0.0 needs 23 other packages to move with it. Restore stays green without them; several would break at runtime.

Nothing new: .popup__list already scrolls at this width for ProjectSelectionPopup. The breadth cap stops the computation from chasing a pathological graph; once it has an answer, showing all of it costs nothing extra — cheaper than a second disclosure to learn (the alternative considered: a short list plus "20 more" behind a click, §107-style) and more honest than refusing to propose past the cap at all, which would turn the common "yes, take the lockstep family" case into a manual per-package chore for no reason beyond the row count.

· What this leaves for whoever implements it

How many hops before the indentation staircase (§2) needs a cap or a different treatment of its own — flagged, not answered, since this file never drew a chain past two hops.
The exact breadth cap number — the mockups use 20/23 to make the point; the issue does not fix a value, and a cap on package count needs a paired thought about how deep a single branch may recurse before the same pathological-graph concern applies to depth instead of breadth.
The nested-tree rendering is proven here on one branch, one level deep. A real closure could nest several branches at once — not yet measured against a real graph from the walk, only reasoned about from how the CSS generalises.
Nothing here designs the reverse-graph walk, the registration paging (inlined vs. multi-page), or the fixpoint/cap algorithm itself — the issue already covers that ground and none of it has a visible surface.
No new colour token is introduced anywhere on this page: every version pair, nested or flat, reuses the same green/gold pairing popup__ver--up/--down already carries, and the dead-end state reuses plain body text. That is why this file is dark-only.
