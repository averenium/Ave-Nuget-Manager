The package list

The left pane of the Packages tab. The panel it lives in is short — usually a bottom panel a few hundred pixels tall — so how many rows fit is the first thing the design is judged on, and today a search result spends a full two-line row to say a package id, a feed name and a version. Everything proposed here is drawn from data the extension already has in state.

What a row costs today

For a search result the left half of line 2 is empty by construction — PackageRow renders the version only when kind !== 'available' — so a quarter of the row is reserved for nothing, and a list of twenty results shows four or five of them.

What the reader cannot tell from this list
— which of these the solution already has. An installed match is listed again in its own section above, with nothing tying the two rows together.
— that the selected one is deprecated. The details panel says so; the row cannot, because AvailableList passes no version flags and PackageRow short-circuits findings for available rows.
— what any of them are. Search returns a description and AvailablePackage.description carries it into state, where nothing renders it.
— why this order. Relevance decides it, but the matched part of each name is not marked, so the ordering looks arbitrary.
— that the list is cut at twenty. The count is shown; that it is a limit rather than a total is not.

2 · Proposed — the same twenty results

The version and the feed join the name on one line, which is where the space already was. The second line exists only when the feed gave a description, and holds one clamped line of it. A package with no description is a single-line row.

Five additions, in order of what they cost
1. The version moves up to the name. Nothing else was using that space, and the second line stops being mandatory. A row with no description drops from 40px to about 24px.
2. The description fills the line it freed. Already in state, never rendered. One line, clamped, never two — a wrapping row would give back everything the first change won.
3. Marks reach available rows. The same glyphs the installed rows already use, so there is nothing new to learn: amber for deprecated, red for an advisory. This is what the HTTP catalog already reads and drops.
4. An installed result says so, and says which version. The badge is the link between the two rows; clicking it selects the installed one.
5. The match is marked, and the cut is stated. The highlight explains the ordering; the footer says twenty is a limit, not a total.

Both panes above are the same height, cut at the same place. Today: five rows. Proposed: seven, three of which carry a description the old one had no room for at all.

3 · Installed — the two versions stop living at opposite edges

The installed and available versions are a two-column grid today, pinned left and right with a variable gap between them, and both wrap mid-string (overflow-wrap: anywhere) when the pane is narrow — which changes the row’s height. Pairing them as one unit is how the Updates tab already shows the same fact.

A version equal to the available one prints once with no arrow rather than twice — the arrow is the thing that means “there is somewhere to go”, and printing 8.0.4 → 8.0.4 spends a row saying nothing.
Several versions across projects keep the amber they have today, in the left half of the pair, where the tooltip still lists them per project.
Versions ellipsize instead of wrapping. A row whose height depends on the pane width makes the list jump while the splitter is dragged, and a version broken across two lines is unreadable anyway.
Implicit rows have no feed and no update, so they are single-line by the same rule as a result with no description — not by a rule of their own.

4 · Narrow — the pane at its 180px minimum

The pane’s width is measured from the longest package id (PackagesTab sizes it from the title row), so the new pieces must never be what decides that width. Each drops in a fixed order as the pane narrows: the description first, the feed name second, the version last — the name and the marks never drop.

At this width the description would be three words and an ellipsis, which is worse than nothing; the feed name is the next least useful, because the source filter above already says which feeds are in play.
The marks stay at every width. They are the only thing in the list that can stop someone installing the wrong thing.

What is deliberately not changed

The order of the sections. Installed, then implicit, then available — putting results first while a query is active would move the list under the reader every time they type.
Hiding an installed package from the results. It would remove the duplicate, but a package that vanishes from a result list reads as “not found”. The badge says the same thing without taking the row away.
The auto-measured pane width. It is computed from the title row, and every addition here either lives on that row and shortens it (the version, already measured), or drops before it can widen anything.
Colour as the only carrier. Marks keep their border and shape so High Contrast themes still show them, as global.css already requires.
Contrast of the list against the search field is #112 and is fixed there, not here.
