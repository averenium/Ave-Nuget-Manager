When one row has several versions

A package resolves per project, and since #82 it can resolve per target framework inside a single project as well. The row has one cell to say that in. Today it enumerates: 2.8.1 / 3.1.0, capped at three and cut with an ellipsis, the whole string amber, with the projects only in the tooltip. Four variants below, each over the same five cases — and each one distinguishing a spread between projects from a spread between frameworks, which the row cannot tell apart at all today.

The rule is not invented here: resolveVersionSpread already picks the primary version for the details panel and already knows withinOneProject — the case where every entry is one project’s and the spread is between its frameworks. Whatever the row shows, it should come from that same call, so the list and the panel can never say different things about the same package.

Rows 1 and 4 are printed identically and mean different things. Row 3 loses two versions to an ellipsis. Nothing says how many projects are on what, so the cell reads as a list of equals when it almost never is.

The slash reads as a fraction or a path. These are alternatives, not a ratio — and the character we use for “or” is the one the rest of the UI uses for file paths.
Everything is amber, so nothing is. The colour marks the condition, but painting all three versions with it leaves no contrast for the one that matters.
The count is missing. Two versions can mean two projects or nine; the row cannot say, and the difference decides whether it is worth acting on.
A framework spread looks like a project spread. One project targeting net8.0 and net10.0 at different versions is a different situation from two projects disagreeing, and often a deliberate one.
