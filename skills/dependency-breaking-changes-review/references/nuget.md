# NuGet: transitives, cache, graph

## Direct vs resolved

`Directory.Packages.props` and `PackageReference` in `*.csproj` are **direct** pins. After restore, **resolved** versions (including transitives) are in `obj/project.assets.json` and `dotnet list --include-transitive`. Requested ranges per consumer (diamonds) are in the same file: `targets` → each library's `dependencies` map (`id` → version range).

`dotnet list --include-transitive` shows the **unified** version only. If two consumers requested different majors for the same id (e.g. Npgsql 9 vs 10) and NuGet unified to one version, that's a **potential runtime incompatibility**, not a confirmed bug and not a compile error — recommend a smoke test on the older consumer's code path.

A failed restore (no assets file) is **Unverified** for the graph, not Compatible. Never start `dotnet build` to get any of this — `obj/project.assets.json` after restore is enough.

## Script (preferred — read this first)

`../scripts/review.fsx`, run with `dotnet fsi` — no project file, no build step, works with any .NET SDK on PATH (`dotnet fsi` has shipped with the SDK since .NET Core 2.1):

```bash
dotnet fsi ../scripts/review.fsx -- diff [<base-ref>] [--no-notes] [--out <dir>]
dotnet fsi ../scripts/review.fsx -- graph <path> [--out <dir>]
dotnet fsi ../scripts/review.fsx -- notes <package-id> <old-version> <new-version>
```

**`diff`** always runs from the repo root (`git rev-parse --show-toplevel`), not wherever it happens to be invoked from — `git diff`'s pathspecs are resolved relative to cwd and restricted to it and below, so running from a project subdirectory would otherwise silently miss a manifest change *above* it (a root `Directory.Packages.props` is exactly this case) with no error to notice. Runs `git diff` (working tree vs `<base-ref>`, or vs `HEAD` if omitted) over `Directory.Packages.props`/`*.csproj`/`*.fsproj`/`*.vbproj` anywhere in the repo, returns `{ packageId, oldVersion, newVersion, changeType, files }` per id (`changeType`: `"changed"` / `"added"` / `"removed"`) — this *is* the manifest-diff read Workflow step 1 asks for. By default every `"changed"` entry also gets a `"notes"` field (below), fetched for every id **in parallel** — so `diff` alone covers steps 1 and 3 in one call. `--no-notes` skips the network fetch but still attaches a `"repo"` field (`repoUrl`/`releasesUrl`/`releaseNotesFromNuspec` — a local nuspec read, no network) to every `"changed"`/`"added"` entry. `"ok": false` (not a git repo, bad ref, `git` not on PATH) → fall back to reading the diff manually (below).

Every `"changed"` entry whose own major version moved also gets `"transitiveMajorHints"` (computed regardless of `--no-notes` — local only, no network, no restore): for each dependency the bumped package's own nuspec declares, it compares the **old** version's declared range against the **new** version's declared range (both nuspecs are typically already in the local cache — the old one from before this bump, the new one from restoring it), and flags any where the declared major itself moved. This is the mechanized form of Rule 3's classic case — EF Core 9 requiring Npgsql 9 directly, with Npgsql never appearing in `Directory.Packages.props` — which `graph`'s diamond/crossing check (below) does **not** catch on its own: that check is internal-graph-consistency only (do two consumers disagree on a version), so a transitive that simply followed its parent to a new major with no other consumer requesting anything different produces no crossing at all. Each hint is `{ packageId, viaDirectPackage, directOldVersion, directNewVersion, oldRequestedRange, newRequestedRange, oldMajor, newMajor, flag: "breaking-candidate" }` — still a candidate, not a confirmed fact (the nuspec's declared range is a floor, not necessarily what actually resolves) — confirm with `graph` and that transitive's own release notes before reporting it as Breaking. If either the old or new nuspec isn't cached locally, this list is simply empty for that id — not an error, just no signal; nothing else in the review depends on it.

**`graph`** restores `<path>` (`.sln`/`.slnx`/`.csproj`/`.fsproj`), parses each project's `obj/project.assets.json` once, and reports:

- **Diamonds** — a package id requested at more than one distinct range by different consumers within that project.
- **Major-version crossings** — a consumer requested major `N`, NuGet resolved major `M ≠ N`. Already flagged `"breaking-candidate"`. When a range/version doesn't parse to a clean major, falls back to the shipped DLL's own assembly version via reflection (metadata read only, does not execute the assembly) before giving up on that one. This is an **internal graph-consistency** check on the current (post-bump) restore only — it does not know what the graph looked like before the bump, so a transitive that simply followed its parent to a new major with nothing else in the graph disagreeing produces no crossing here. That case is `diff`'s `"transitiveMajorHints"` (above), not this.

Replaces `dotnet nuget why <path> <id>` per shared/transitive id with one pass.

**`notes`** — the same per-package lookup `diff` embeds, callable standalone for re-checking one id. Resolves the package's repo from the already-restored local NuGet cache (`~/.nuget/packages/<id>/<new-version>/<id>.nuspec` — `<repository url>`/`<projectUrl>`, and `<releaseNotes>` checked directly, no network), then lists releases/tags in range from whichever of GitHub/GitLab/Bitbucket/Azure DevOps the repo is hosted on, pre-scanned for risk markers (`breaking`, `removed`, `renamed`, major dependency bump, `+semver:major`). Bitbucket/Azure DevOps expose tags only, no changelog body — those need a manual read same as a changelog-less tag on any host. `"releasesUrl"` (the host's actual releases page, e.g. `.../releases`, not the repo root) is computed from the repo URL alone with no network call, so it's set whenever the repo is known — a concrete link even when the fetch itself failed or was rate-limited. On GitHub the release list needs **no credential at all**: it is scraped from the public releases page (`github.com/<owner>/<repo>/releases?page=N`), walking pages back until it passes `oldVersion`. That is the web app, not `api.github.com`, so it is outside the REST quota entirely — a 20-package review resolves every id in one pass with nothing exported. The script never reaches for a credential on its own (it does **not** shell out to `gh auth token`); `GITHUB_TOKEN` is honoured only when whoever ran it chose to export it, and now matters solely for the two remaining API calls, both on the tags-without-Releases path: the tag list and the `compare` commit log.

If the scrape fails (network, or GitHub changed the release-page markup), `notes` falls back to `github.com/<owner>/<repo>/releases.atom` — same origin, also token-free, and a stable XML shape that survives HTML changes, but genuinely incomplete: that feed only ever lists the **~10 most recent releases** with no reliable way to page further back. `"incompleteSource"` names which source was used and why the list may be short — `"atom-feed"` (scrape failed) or `"page-limit"` (the walk hit its 30-page cap without reaching `oldVersion`) — and `"resolution"` drops to `"partial"` (never `"ok"`) whenever it is set, even when releases were found. Treat either as a partial candidate, not the authoritative range, and check the releases page by hand before concluding — same spirit as any other `"partial"` resolution.

GitHub specifically: a repo can keep tagging every version while no longer creating a "Release" object for some/all of them (observed live reviewing real bumps — `TelegramBots/Telegram.Bot` and `npgsql/efcore.pg` both had the target version tagged with zero matching Release). When `newVersion`'s own tag isn't covered by any Release, `notes` resolves that tag and `oldVersion`'s tag from `/tags` and pulls the raw commit log between them in one `compare` call — `"commitFallback"` (`{ sha, message, hasRiskMarker }` per commit, first line of the message only), pre-scanned for the same risk markers as a release body, plus `"commitsCompareUrl"` (`.../compare/<oldTag>...<newTag>`) as a concrete link even if the compare call itself fails. This is what replaces manually running `gh api .../releases`, `.../tags`, or `.../compare/<old>...<new> --jq '.commits[].commit.message'` by hand when the Releases API alone comes up short. `"resolution"` is `"ok"` whenever either `"releases"` or `"commitFallback"` has entries — read both, they can cover different parts of the same range (e.g. one patch has a Release, the next doesn't). Not attempted on GitLab/Bitbucket/Azure DevOps yet.

**Read `"commitFallback"`/`"releases"` before reaching for anything external — do not guess a versioned documentation URL.** Observed live: with nothing to go on but the package's own project page, three separate `WebFetch` calls each guessed a plausible-looking versioned doc URL (a migration-guide page for a specific version range, a per-minor release-notes page) — all three came back empty or 404, and the review still ended up running `gh api .../compare --jq '.commits[].commit.message'` by hand afterward, which is exactly what `"commitFallback"` already is. The rule this argues for: `"commitFallback"`/`"releases"` (already risk-marker-scanned) is the first and normally sufficient source for a GitHub id — read it before trying anything else. Only when it's genuinely empty (a non-GitHub host, or the API call itself failed) does an external doc site become worth a look, and even then check one root/index page for the project's docs first (it usually says whether per-version pages exist at all and what they're named) rather than constructing a versioned path (`/22x.html`-style) with nothing on hand confirming that pattern — a wrong guess is a full fetch-and-summarize round trip for nothing, same cost as the real one that would have worked.

When no release/tag list resolves at all (no repo, unsupported host, the API call failed, or GitHub commit-compare also came up empty), it checks one more local source before giving up: a bundled `CHANGELOG.md`/`RELEASENOTES.md`-style file inside the already-restored `.nupkg` (package root, `content/`, `contentFiles/`, `lib/`, up to 3 levels deep). Found → `"localChangelogFile"`/`"localChangelogPreview"` (first ~1000 chars; read the full file for the rest) are set and `"resolution"` becomes `"partial"`.

**The script never silently returns nothing.** `"resolution"` is always one of `"ok"` (a release list and/or a GitHub commit-log fallback), `"partial"` (nuspec notes and/or a bundled changelog, no structured release/commit list), or `"unresolved-manual-required"` (`"fallbackHints"`: `"releasesUrl"` if known, else the NuGet.org package page, plus whether the API call failed). `"unresolved-manual-required"` is **not** permission to write Unverified — still try a migration guide, a downstream package's own notes, or direct API usage in this repo before concluding Unverified.

**`--out <dir>`** (either subcommand) — a **directory**, not a file: writes `<dir>/diff.json`/`<dir>/graph.json` (the full, pretty-printed result — grep/jq this) **and** `<dir>/diff.md`/`<dir>/graph.md` (the same data as a report skeleton: mechanical facts filled in per id/project, an explicit `TODO`/`Verdict` line where the job needs the agent's own judgment or a codebase cross-check) side by side, with only a short summary (counts + both file paths) on stdout — for a bump touching many ids, or `graph` on a large solution, so the whole JSON doesn't have to pass through the conversation. The next step is opening the `.md` and filling in what only the agent can do — not reformatting the JSON into prose first, and not treating the `.md` as optional reading either; it's the same data, laid out for editing rather than querying. Point `--out` at a **timestamped scratch directory in the workspace root** — `.dependency-review-YYYYMMDD-HHMMSS/` — not at the report path, and delete that directory once the report is finished, unless the user asked to keep the working artifacts. Inside the workspace rather than a system temp path because write access there is what can actually be relied on (and `dotnet fsi`, being a .NET process, cannot resolve a Git-Bash `/tmp/…` path in the first place). These are one review's working files; only the dated report is a deliverable, and aiming `--out` at `docs/dependency-reviews/` leaves all of them next to it to be committed by accident.

`diff --out` writes a third file, **`<dir>/release-notes.md`**: every in-range release's notes in full, formatted for a person. It exists because the two audiences want opposite things — the agent needs the least text that still supports a verdict, the reader wants the actual published notes to check that verdict against. So `diff.md` cuts a *non-flagged* release's body to a one-line excerpt (those lists are usually Dependabot `Bump …` noise; reading them whole was the largest single line item in one real review's token spend, and a flagged release still shows its body in full), while `release-notes.md` keeps everything. Append it to the finished report as the last section with a shell redirect — `cat <dir>/release-notes.md >> <report>.md` — and **never `Read` it**: routing it through the conversation to "include" it is exactly the cost the split exists to avoid.

**Reading the `.json` back — never a plain, unbounded `Read`.** That silently defeats the whole point of `--out`: a `Read` with no `offset`/`limit` reads from the top, and on a large `diff` (many changed ids, most with a `"notes"` block full of `bodyPreview` text) it can burn most of the context window on tool output before even reaching the tool's own output cap — observed live: a first, unbounded `Read` got cut off after 450 of 2056 lines, already consuming the bulk of what should have been a cheap, targeted lookup. Instead:

1. `grep -n` (or `jq`, or a one-off Python/Node script) for exactly what's needed — `"packageId": "<id>"` for one package, `"hasRiskMarker": true` to jump straight to the releases/commits actually worth reading, `"resolution"` not matching `"ok"` for the ones that need the fallback chain. The file is pretty-printed (one field per line), so `grep -n` gives usable line numbers directly.
2. Only then `Read` with a precise `offset`/`limit` bracketing those line numbers (the enclosing JSON object is a bounded number of lines either side) — not the file from line 1.

**If `dotnet fsi` is unavailable, or any subcommand errors** — fall back to the manual steps below. Never skip Rule 4 (or Rule 2's range read) just because the script didn't run.

## Manual fallback (script unavailable only)

```bash
dotnet restore
dotnet list <path> package --include-transitive
dotnet nuget why <path> <package-id>   # shared ids, and any transitive whose major moved
```

`<path>` is a `.sln`/`.slnx`/`.csproj`/`.fsproj`. If `packages.lock.json` is in the diff, `git diff` that file first (old/new transitives without restoring). Read `obj/project.assets.json` next to each relevant project for `libraries` (resolved) and `targets → dependencies` (requested ranges, i.e. diamonds) — same data `graph` parses automatically.

For notes: GitHub **release/tag** URL for that version, not the Releases index (truncates "Breaking Changes"); confirm an aggregated/milestone view actually starts at or before the **old** version (pagination often shows only recent tags); repo `CHANGELOG.md` if tags are sparse; umbrella changelogs (e.g. Aspire wiki) count for every id they list. No public repo, or nothing readable there → inspect `~/.nuget/packages/<id>/<version>/` for `CHANGELOG.md`/`RELEASENOTES.md` (root, `content/`, `contentFiles/`, `lib/`) and the `.nuspec`'s `<releaseNotes>` — same fallback `notes` already does automatically. Never skip an id only because it has no public repo; mark **Unverified** and say the cache was inspected if nothing is there.

## Old vs new transitives (Rule 3)

The manifest diff doesn't list transitives, and `bin/` is almost never in git — the **old** transitive version is often unknown; say so, but still scan recent releases of the transitives in scope (Rule 2). The **current** tree comes from `graph`. Under a majorly-bumped direct package (or a transitive major `graph` revealed), pick the handful of transitives the app code is actually exposed to (DB driver, HTTP, serialization) — not every leaf.
