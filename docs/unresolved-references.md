# Посилання, яке restore не зміг розв'язати (#138)

Панель показувала лише те, що є в графі restore. `dotnet list package --no-restore` читає `obj/project.assets.json`, а restore, що впав на `NU1101` (немає пакета) чи `NU1102` (немає версії), не кладе такий пакет ні в `targets`, ні в `libraries` — команда виходить з кодом 0 без жодної згадки. Посилання зникало з панелі зовсім.

## Звідки береться відповідь

- **`obj/project.nuget.cache`** (`src/restoreOutcome.ts`): поруч із файлом, який розширення вже читає. `logs` із `level: Error` та полем `libraryId` дають код, id, фреймворки (`targetGraphs`) і формулювання самого фіду. Відсутній чи зіпсований файл — «нічого не відомо», а не «щось не так».
- **Оголошені посилання** (`src/declaredReferences.ts`): `<PackageReference Include>` проєкту (коментарі замасковані; `Update` і id з `$(…)` не рахуються). Версія — з проєкту, інакше `VersionOverride`, інакше з `Directory.Packages.props` (CPM), інакше порожня. Посилання з `Condition` (власним чи групи) позначене `conditional`.
- **Різниця** (`src/unresolvedReferences.ts`): оголошене, але відсутнє в списку проєкту. Причина — запис у логах кешу; без нього «not restored yet», якщо файл проєкту (чи props) новіший за кеш, і ніщо, якщо ні. Умовні посилання без помилки в логах «не відновленими» не вважаються: вони можуть просто не діяти.

## Куди це йде

Окремо від списку встановлених: `INSTALLED_PACKAGES.unresolved` → `state.packages.unresolved`. Не змішується з `installed`, бо все, що читає той список (оновлення, групи, перевірка залежних), не має його бачити. Панель деталей об'єднує обидва списки для вибраного пакета: версія в пікері, «Remove», рядки проєктів.

## Як це виглядає

За макетом `docs/design/unresolved-package-references.html`: секція «Unresolved N» над «Installed» (тільки коли є що показати), той самий рядок: id і скісна риска в колі (колір помилки), зліва заявлена версія, справа причина (`not found` для NU1101, `no such version` для NU1102, `restore failed` для інших кодів, `not restored yet` без помилки). У панелі — смуга з кодом, повідомленням і фреймворками під рядком версії (поза блоком метаданих, бо для NU1101 його немає), для кількох проєктів — повідомлення під рядком проєкту. «Not restored yet» — нейтрально, лише рядок під версією.

## Межі й рішення

- **Проєкт, у якому не відновилось нічого.** `dotnet list --no-restore` відповідає на такий проєкт кодом 0 і без пакетів (проєкт у відповіді є, з його `framework`), а `_toListResult` у `cliBackend.ts` без пакетів повертає результат без `projectFrameworks`, тож ні список, ні `projectFrameworks` проєкт не називають. Проєкти беруться ще й з області перегляду (`_unresolvedOf`), інакше такий проєкт виглядав би порожнім, як і до зміни.
- **Старе повідомлення біля нової версії.** Помилка з логів кешу виграє у «not restored yet», крім одного випадку: файл відредаговано після restore, а `NU1102` у повідомленні (`(>= 99.99.99)`) називає версію, відмінну від оголошеної зараз. Тоді повідомлення про стару версію не показується, рядок нейтральний. Нижню межу читають із дужок наприкінці повідомлення, а не з тексту навколо (він залежить від мови SDK): `(>= v)` для голої версії, `(= v)` для `[v]`, `(> v)` для `(v, )`, `(>= a && < b)` для інтервалу — виміряно на англійському SDK; порівнюється з нижньою межею оголошеного діапазону. Якщо порівнювати нічого (немає межі, плаваюча версія `1.*`) — повідомлення лишається. `NU1101` стосується id, тож правка версії його не скасовує.
- **Посилання з `Directory.Build.props` / `.targets`** не мають рядка: розбирається лише сам файл проєкту (і `Directory.Packages.props` для версій). Remove для такого посилання все одно б не спрацював, тож це межа обсягу.
